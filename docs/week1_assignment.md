# 필수 과제

## 1. 게시글 기능 재정리

현재 코드 기준으로 게시글과 관련된 핵심 기능은 작성, 전체 조회, 단건 조회, 수정, 삭제입니다. 사용자는 글을 작성할 수 있어야 하고, 작성된 글 목록을 볼 수 있어야 하며, 특정 글 하나를 자세히 조회할 수 있어야 합니다. 또한 기존 글의 제목과 내용을 수정할 수 있어야 하고, 더 이상 필요하지 않은 글은 삭제할 수 있어야 합니다.

실서비스 관점에서 추가로 있으면 좋은 기능으로는 검색, 정렬 및 페이징, 작성자 권한 체크, 댓글, 좋아요, 신고 기능 등이 있습니다. 다만 현재 과제 범위에서는 CRUD를 우선적으로 충실하게 구현하는 것이 핵심입니다.

### 저장해야 하는 데이터

현재 `Post` 도메인 기준으로 저장해야 하는 데이터는 아래와 같습니다.

- `id`: 게시글을 식별하는 고유값
- `title`: 게시글 제목
- `content`: 게시글 내용
- `author`: 작성자 이름
- `createdAt`: 작성 시각

즉, 게시글은 "누가, 언제, 어떤 제목과 내용으로 작성했는가"를 저장해야 합니다.

### 요청해야 하는 데이터

기능별로 필요한 요청 데이터는 다음과 같습니다.

- 작성 요청: `title`, `content`, `author`
- 전체 조회 요청: 별도 본문 데이터 없음
- 단건 조회 요청: `id`
- 수정 요청: `id`, `title`, `content`
- 삭제 요청: `id`

현재 코드에서는 작성 시 `CreatePostRequest`, 수정 시 `UpdatePostRequestDto`를 사용하고 있습니다.

### 응답해야 하는 데이터

기능별 응답 데이터는 아래처럼 정리할 수 있습니다.

- 작성 응답: 생성된 게시글 `id`, 처리 결과 `message`
- 전체 조회 응답: `success`, `message`, `data(List<ReadPostResponseDto>)`
- 단건 조회 응답: `success`, `message`, `data(ReadPostResponseDto)`
- 수정 응답: `success`, `message`
- 삭제 응답: `success`, `message`

현재 조회/수정/삭제는 공통 응답 객체인 `commonResponse<T>`를 사용하고 있고, 조회는 실제 게시글 데이터를 `data`에 담아 반환합니다. 수정과 삭제는 추가 데이터가 필요하지 않아서 메시지 중심으로 응답합니다.

### 검증해야 하는 조건

현재 코드 기준으로 반드시 검증해야 하는 조건은 다음과 같습니다.

- `title`은 비어 있으면 안 된다.
- `content`는 비어 있으면 안 된다.
- 조회, 수정, 삭제 시 요청한 `id`에 해당하는 게시글이 실제로 존재해야 한다.

존재하지 않는 게시글 ID에 대해서는 `PostNotFoundException`을 통해 예외를 처리하고 있습니다.

추가로 있으면 좋은 검증 조건은 아래와 같습니다.

- `author`도 비어 있지 않은지 확인
- 제목 최대 길이 제한
- 내용 최대 길이 제한
- 수정 시 제목/내용이 모두 공백이 아닌지 확인
- 삭제/수정 권한이 있는 작성자인지 확인

# 키워드 과제
## 1. `final` / `static` / `static final` 차이

### `final`

`final`은 "한 번 정해지면 더 바꿀 수 없게 제한하는 것"입니다.

- 변수에 붙으면: 한 번 값이 정해진 뒤 재할당할 수 없습니다.
- 메서드에 붙으면: 자식 클래스에서 오버라이딩할 수 없습니다.
- 클래스에 붙으면: 상속할 수 없습니다.

현재 코드에서는 `UpdatePostRequestDto`의 필드들이 `final`로 선언되어 있어서, 생성자에서 값이 정해진 뒤에는 바뀌지 않습니다.

### `static`

`static`은 "객체마다 따로 존재하는 값이 아니라 클래스 자체에 속하는 값 또는 메서드"라는 뜻입니다.

- `static` 변수는 객체를 여러 개 만들어도 하나만 공유됩니다.
- `static` 메서드는 객체 생성 없이 클래스 이름으로 바로 호출할 수 있습니다.

예를 들어 `Main`의 `main` 메서드는 프로그램 시작점이기 때문에 `static`입니다. 또 `PostRepository`의 `postList`는 `static`으로 선언되어 있어, 저장소 객체가 달라도 같은 리스트를 공유합니다.

### `static final`

`static final`은 "클래스 전체에서 하나만 존재하고, 값도 바뀌지 않는 상수"를 의미합니다.

보통 아래처럼 사용합니다.

```java
private static final int MAX_TITLE_LENGTH = 50;
```

즉, `static`은 공유, `final`은 변경 불가, `static final`은 "공유되는 상수"라고 이해하면 됩니다.

## 2. Java의 Generic 타입이란?

Generic은 "타입을 미리 구체적으로 정하지 않고, 사용할 때 결정할 수 있게 만든 문법"입니다.

예를 들어 `List<Post>`에서 `<Post>`는 이 리스트가 `Post` 타입만 담겠다는 뜻입니다. 즉, 아무 객체나 넣는 것이 아니라 `Post`만 저장할 수 있도록 타입을 제한하는 것입니다.

Generic을 쓰는 이유는 다음과 같습니다.

- 타입 안정성이 높아집니다.
- 잘못된 타입이 들어가는 실수를 컴파일 시점에 잡을 수 있습니다.
- 형변환(casting)을 줄일 수 있습니다.
- 같은 구조를 여러 타입에 재사용할 수 있습니다.

현재 코드에서 볼 수 있는 예시는 아래와 같습니다.

- `List<Post>`: `Post` 객체만 담는 리스트
- `List<ReadPostResponseDto>`: 조회 응답 DTO만 담는 리스트
- `commonResponse<T>`: 어떤 타입의 응답 데이터든 담을 수 있는 공통 응답 객체
- `commonResponse<Void>`: 데이터는 없고 성공 여부와 메시지만 표현하는 응답

만약 Generic 없이 `Object`로만 처리하면, 꺼낼 때마다 형변환이 필요하고 실수할 가능성이 커집니다. 반면 Generic을 쓰면 "무슨 타입이 들어가는지"가 코드에 명확하게 드러납니다.

## 3. Controller / Service / Repository / Domain 역할

### Controller

Controller는 사용자의 요청을 가장 먼저 받고, 그 요청을 어떤 서비스로 넘길지 결정하며, 최종적으로 어떤 응답 형식으로 반환할지 정리하는 계층입니다. 현재 코드에서는 `PostController`가 이 역할을 합니다. 또한 예외가 발생했을 때 실패 응답 메시지로 바꾸는 책임도 일부 맡고 있습니다.

### Service

Service는 실제 비즈니스 로직을 처리하는 계층입니다. 게시글을 조회할지, 수정할지, 삭제할지, 어떤 검증을 거쳐야 하는지 같은 처리 흐름이 여기에 들어갑니다. 현재 코드에서는 `PostService`가 게시글 목록을 관리하고, 검증기(`PostValidator`)를 호출하고, 게시글을 찾고 수정/삭제하는 역할을 맡고 있습니다.

### Repository

Repository는 데이터를 저장하고 꺼내는 역할을 맡는 계층입니다. 보통 데이터베이스와 가장 가까운 계층이라고 생각하면 됩니다. 현재 코드에는 `PostRepository`가 정의되어 있고, 저장, 전체 조회, 단건 조회, 삭제 기능을 메서드로 갖고 있습니다.

다만 현재 프로젝트에서는 `PostService`가 아직 직접 `List<Post>`를 들고 있어서, `Repository` 역할이 완전히 분리되어 있지는 않습니다. 즉, 구조는 준비되어 있지만 실제 사용은 아직 서비스 중심으로 되어 있습니다.

### Domain

Domain은 서비스가 다루는 핵심 데이터 자체를 표현하는 계층입니다. 현재 코드에서 `Post`는 게시글 하나를 표현하는 도메인 객체입니다. 게시글이 가져야 하는 속성(`id`, `title`, `content`, `author`, `createdAt`)과 게시글이 스스로 할 수 있는 동작(`update`)이 여기에 들어 있습니다.

정리하면 다음과 같습니다.

- Controller: 요청/응답 처리
- Service: 비즈니스 로직 처리
- Repository: 데이터 저장소 접근
- Domain: 핵심 데이터와 상태 표현

이렇게 역할을 나누면 코드 책임이 분명해지고, 수정이나 확장이 쉬워집니다.
